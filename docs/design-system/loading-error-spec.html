Section 01

Loading & Error State Unification

A systematic approach to loading, error, and empty states across the DRMS application. Three tiers for loading, three tiers for errors, one canonical implementation per pattern.

Problem Statement

DRMS currently has at least six different loading patterns and four different error patterns spread across 90+ locations. Hand-crafted animate-pulse divs, inconsistent spinner placements, and ad-hoc error cards create a fragmented user experience and significant maintenance overhead.

Scope

This specification defines the unified loading and error state system for Phase 6 of the DRMS Design System. It covers three tiers of loading indicators (full-page, content-area, inline), three tiers of error handling (full-page, content-area, toast), and references the existing empty state component.

Section 02

Research Sources

Loading and error states are not merely decorative -- they directly affect perceived performance and user trust. The following research informs the design decisions in this specification.

Skeleton Loading Patterns

Facebook pioneered the skeleton screen concept in 2013, showing wireframe placeholders instead of spinners. Luke Wroblewski documented that skeleton screens feel 30% faster than spinners because they prime the user for the content layout that will appear.

Source: Luke Wroblewski, "Mobile Design Details: Inline Spinners vs Skeleton Screens"

NN/g Response Time Limits

Three critical thresholds: 0.1s feels instant (no feedback needed), 1s keeps user flow (subtle indicator), 10s loses attention (explicit progress required). These thresholds map directly to our 3-tier loading system.

Source: Nielsen Norman Group, "Response Times: The 3 Important Limits"

Material Design Progress Indicators

Google's Material Design defines linear progress bars for deterministic operations and circular indicators for indeterminate loading. Skeleton shapes (rectangles and circles) represent the content that will load.

Source: Material Design 3, Progress Indicators

Ant Design Skeleton Component

Ant Design provides a Skeleton component with pre-built shapes for avatars, paragraphs, buttons, inputs, and images. The active prop enables shimmer animation. This pattern inspired our ContentSkeleton presets.

Source: Ant Design 5.x, Skeleton Component

Shopify Polaris Loading / Empty / Error States

Shopify Polaris separates loading, empty, and error into distinct components with clear guidelines: skeleton loading for initial page loads, spinner for inline actions, and structured empty states with calls to action.

Source: Shopify Polaris, Loading & Empty State Patterns

Carbon Design System -- Loading & Inline Notification

IBM's Carbon Design System uses inline loading states (small spinner + text), skeleton placeholders, and a four-variant notification system (info, success, warning, error) that maps well to our error tier approach.

Source: Carbon Design System, Loading & Inline Notification

Apple HIG -- Loading & Content Views

Apple's Human Interface Guidelines recommend using progress indicators for operations longer than a few seconds, and designing empty states that educate and guide users toward their first action.

Source: Apple HIG, Loading & Content Views
Section 03

Design Principles

1. Context-appropriate loading

Full-page spinner for route transitions. Skeleton shapes for content areas. Inline spinners for button/async actions. Never use a full-page spinner when only a section is loading.

2. Progressive loading feedback

0--300ms: no indicator needed (feels instant). 300ms--1s: subtle skeleton shapes. 1s+: skeleton with progress text ("Loading dashboard..."). 10s+: explicit progress bar with percentage or estimated time.

3. Recoverable error states

Every error state must offer a clear next action: retry the operation, navigate back, or contact support. Never show an error without a path forward. Error messages should be human-readable, not raw API responses.

4. One canonical implementation per pattern

No more ad-hoc animate-pulse divs or copy-pasted error cards. Every loading pattern maps to one component. Every error pattern maps to one component. Variations are handled through props, not duplicate implementations.

Section 06

Loading States: 3-Tier System

1 Tier 1: Full-Page Loading

Route transitions, initial data load. The entire content area shows a single loading indicator.

  • Component: SafeDataLoader (enhanced)
  • Visual: Centered Loader2 spinner (h-8 w-8) + loading message text
  • Enhancement: Add skeleton prop to SafeDataLoader that renders skeleton shapes instead of spinner when context requires it
  • Use: Page-level wrapping for data-dependent pages
// Tier 1: Full-page loading via SafeDataLoader <SafeDataLoader query={useDashboardData()} loadingMessage="Loading dashboard..." skeleton="card" // NEW: optional skeleton preset > {(data) => <DashboardContent data={data} />} </SafeDataLoader>

2 Tier 2: Content-Area Loading

Cards, panels, sections within a page. Only the loading section shows a skeleton; the rest of the page remains interactive.

  • Component: ContentSkeleton (new) -- wraps shadcn <Skeleton>
  • Visual: animate-pulse rounded-md bg-muted shapes
  • Presets: card, table, list, metric, form
  • Use: Inside components, replacing all 35+ ad-hoc animate-pulse divs
// Tier 2: Content-area skeleton presets <ContentSkeleton variant="card" /> <ContentSkeleton variant="table" rows={5} cols={4} /> <ContentSkeleton variant="list" count={3} /> <ContentSkeleton variant="metric" count={4} /> <ContentSkeleton variant="form" />

3 Tier 3: Inline Loading

Buttons, small async actions. A spinner replaces the button icon while the action is in progress.

  • Component: <Loader2 className="h-4 w-4 animate-spin" />
  • Convention: Always paired with a text change ("Saving..." vs "Save")
  • Use: Form submit buttons, inline save actions
// Tier 3: Button loading convention <Button disabled={isSubmitting}> {isSubmitting ? ( <> <Loader2 className="mr-2 h-4 w-4 animate-spin" /> Saving... </> ) : ( "Save" )} </Button>
Section 07

Error States: 3-Tier System

1 Tier 1: Full-Page Error

Critical failures where no data is available. The entire page shows an error state with recovery actions.

  • Component: Enhanced error.tsx boundaries
  • Visual: Centered error icon + title + description + "Try Again" button + navigation link
  • Enhancement: Use shadcn Button (not raw <button>), add "Go to Dashboard" navigation link
  • Use: Route-level error boundaries

2 Tier 2: Content-Area Error

Component-level failure where the rest of the page still works. An inline error alert with retry capability.

  • Component: ErrorAlert (new) -- wraps shadcn <Alert variant="destructive">
  • Visual: AlertTriangle icon + title + message + optional Retry button
  • Use: Inline within components, form-level errors
// Tier 2: Content-area error alert <ErrorAlert title="Failed to load data" message={error.message} onRetry={refetch} variant="destructive" />

3 Tier 3: Toast Error

Transient failures from background operations that do not block the UI.

  • Component: toast.error() from Sonner
  • Visual: Red-themed toast with error icon, auto-dismiss after 5s
  • Use: API call failures that don't block the UI (save failures, sync errors)
// Tier 3: Toast error toast.error("Failed to save changes", { description: "Your changes were not saved. Please try again.", });

Section 10

Component API

ContentSkeleton

interface ContentSkeletonProps { variant: 'card' | 'table' | 'list' | 'metric' | 'form'; rows?: number; cols?: number; count?: number; className?: string; }
Prop Type Default Description
variant 'card' | 'table' | 'list' | 'metric' | 'form' -- Skeleton shape preset. Required.
rows number 3 Row count for table variant.
cols number 4 Column count for table variant.
count number 3 Item count for metric/list variants.
className string undefined Additional CSS classes merged via cn().

ErrorAlert

interface ErrorAlertProps { title: string; message?: string; onRetry?: () => void; variant?: 'destructive' | 'warning'; className?: string; }
Prop Type Default Description
title string 'Error' Alert title. Always visible.
message string undefined Error description displayed below the title.
onRetry () => void undefined Retry callback. When provided, shows a "Retry" button.
variant 'destructive' | 'warning' 'destructive' Alert color scheme. Destructive = red, warning = amber.
className string undefined Additional CSS classes merged via cn().
