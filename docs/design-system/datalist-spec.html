DataList Component Family

Phase 3 design spec for DRMS data display components. All variants share the same shadcn/ui visual DNA.

PHASE 3 — REV 2

1. Research Sources

  • Ant Design Data Display — Table, List, Card patterns; row selection, inline actions, batch operations
  • NN/g Data Tables — Scanning vs comparing; progressive disclosure; sortable columns for comparison tasks
  • Material Design M3 — DataTable (comprehensive), CardList (reading), CardGrid (browsing), Config forms
  • Shneiderman's Information-Seeking Mantra — Overview first, zoom/filter, details on demand
  • OCHA Humanitarian Data Management — Severity-first display, role-based density, incident tracking
  • ISCRAM Emergency Response Patterns — Sitrep tiles, rapid scan, action-oriented cards

2. Core Principles

Comparison drives layout

When users need to compare items across the same attributes, use a table. When they read items independently, use cards.

Density matches task

Operational monitoring needs high density (tables). Browsing and selection needs scannable tiles (card grids).

Progressive disclosure

Show the minimum needed for the current task. Details, history, and secondary info are revealed on interaction.

Structure, not content, decides

Variant is chosen by the shape of the data and the user's task — not by what the data is about.

Config is not a list

Settings/thresholds are editable key-value pairs, not browsable data items. They get their own pattern.

One design system, four layouts

All variants share the same tokens, border radius, shadows, fonts, spacing, and color system. Only the layout differs.

3. Variant Decision Logic

Q1: Do items share the same fields? Yes → Q2: Is the task comparison or editing?
Comparison → DataTable
Inline editing → DataConfig
Q1 answer: No (fields vary per item) → Q3: Visual tiles or sequential reading?
Tiles / browse → DataCardGrid
Sequential → DataCardList

Expand/Collapse Behaviour (DataTable)

  • Trigger: Chevron button (ghost variant, 28px) in the first column. Collapsed = chevron-right, Expanded = chevron-down (rotated 90deg).
  • Expanded row: A full-width <tr> below the parent with colSpan spanning all columns. Background: bg-muted/30 (subtly tinted). Hover removed on expanded rows.
  • Content: Two-column grid with detail fields and linked records. Padding indented to align with text columns.
  • No animation: Content appears instantly (matches existing codebase convention).
  • State: expandedRows: Set<string> in component state.

DRMS Pages Using DataTable

  • Users — same columns for all rows, sort/filter/compare
  • Roles & Permissions — tabular RBAC management
  • Database Tables — system admin table browser
  • Incident Management — expandable rows for incident details + linked assessments

Severity Indication (No Side Accent)

  • Background tint: The entire card gets a very subtle severity-tinted background (4% opacity). This creates an at-a-glance color association without the heavy left-border pattern.
  • Severity badge: StatusBadge component with severity colors provides explicit labeling.
  • Expand chevron: Positioned inline with the badge row for clean alignment.

Expand/Collapse Behaviour (DataCardList)

  • Trigger: Chevron button at the start of each card, aligned with the badge/title row.
  • Collapsed: Shows badge + title + metadata row + action buttons. Consistent card shape for all items.
  • Expanded: A bordered section appears below the metadata, with a 2-column detail grid. Actions move to the bottom of the expanded section.
  • State: expandedItems: Set<string>

DRMS Pages Using DataCardList

  • Verification Queue — varying severity + context, sequential review, expand for details
  • Commitment Dashboard — each commitment has different status + detail
  • Configuration Audit History — chronological event cards
  • Incident Management — expandable incident cards with severity tint
  • Leaderboard — ranked donor cards with position indicators

Design Rationale (DataCardGrid)

  • Single primary metric + progress bar: Each card shows ONE key metric (fulfillment rate) with a visual progress bar. This gives instant scannability — users can compare cards by bar length at a glance.
  • Supporting context: Secondary text below the bar provides commitment count and value. No 2x2 stat grid — that created visual noise.
  • Entity identity top-left, status top-right: Consistent card header layout — name/region on the left, status badge on the right.
  • Selected state: Border color changes to primary/30 to indicate selection (see Card 1).

DRMS Pages Using DataCardGrid

  • Entity Insights — browse entities with key metrics, click to drill down
  • Executive Incidents — situation-awareness tiles with severity indicators
  • Peer Comparison — side-by-side donor metric cards

8. Feature: Expand/Collapse

Expand/collapse is a feature of DataCardList and DataTable, not a separate variant. Both use the same interaction pattern, adapted to their layout.

Trigger pattern

Ghost-variant chevron button (28px). Collapsed = chevron-right icon. Expanded = rotated 90deg to point down. Uses e.stopPropagation() to prevent parent click handlers.

Expanded content

Two-column responsive grid (grid-cols-1 md:grid-cols-2) with labeled fields. Shows additional data not visible in collapsed state: descriptions, linked records, timelines.

Visual separation

DataTable: bg-muted/30 background on expanded row. DataCardList: border-top separator with padding. Both clearly distinguish expanded content from summary.

State management

expandedItems: Set<string> tracked in component state. Toggle function creates a new Set, adding/removing the item ID. Multiple items can be expanded simultaneously.

No animation

Content appears/disappears instantly via conditional rendering. Matches the existing codebase convention in IncidentManagement and VerificationQueue components.

Collapsed consistency

When all items are collapsed, DataCardList items all share the same card shape. This makes the list scannable — users can quickly compare summaries before expanding the ones they need.

12. Component API

DataTable

interface DataTableProps<T> { columns: ColumnDef<T>[] // Column definitions (TanStack Table) data: T[] loading?: boolean // Shows skeleton rows emptyMessage?: string // Shown when data is [] searchable?: boolean // Adds search input in toolbar filterable?: FilterConfig[] // Adds select dropdowns selectable?: boolean // Checkbox column expandable?: boolean // Adds expand/collapse chevron column renderExpanded?: (row: T) => ReactNode // Content for expanded row pagination?: PaginationConfig // Page size, total count onRowClick?: (row: T) => void actions?: RowAction[] // DropdownMenu items }

DataCardList

interface DataCardListProps<T> { data: T[] loading?: boolean emptyMessage?: string renderCard: (item: T, ExpandedCardProps) => ReactNode // Card renderer with expand API getSeverity?: (item: T) => SeverityLevel // For background tint expandable?: boolean // Enables expand/collapse renderExpanded?: (item: T) => ReactNode // Expanded detail content searchable?: boolean pagination?: PaginationConfig cardPadding?: 'sm' | 'md' | 'lg' // Default: md (p-4) } interface ExpandedCardProps { isExpanded: boolean toggleExpand: () => void }

DataCardGrid

interface DataCardGridProps<T> { data: T[] loading?: boolean emptyMessage?: string columns?: 2 | 3 | 4 // Grid columns, default 3 renderCard: (item: T) => ReactNode onCardClick?: (item: T) => void selectedId?: string // Highlights selected card (border-primary/30) searchable?: boolean }

DataConfig

interface DataConfigProps { title: string description?: string fields: ConfigField[] // Key-value field definitions values: Record<string, unknown> // Current values onSave: (values: Record<string, unknown>) => void onReset?: () => void loading?: boolean } interface ConfigField { key: string label: string description?: string type: 'number' | 'select' | 'toggle' | 'text' severity?: SeverityLevel // For status dot + badge options?: { label: string; value: string }[] defaultValue?: unknown }

SearchToolbar (cross-cutting)

interface SearchToolbarProps { searchPlaceholder?: string onSearchChange?: (value: string) => void filters?: FilterConfig[] onFilterChange?: (key: string, value: string) => void actions?: ToolbarAction[] // Reset, Export, etc. } interface FilterConfig { key: string label: string options: { label: string; value: string }[] }
