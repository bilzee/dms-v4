# Story 9.1: Signal Analytics Backend

## Status
Ready

## Story
**As a** coordinator,
**I want** to query historical signal analytics with volume, resolution velocity, and engagement metrics,
**so that** I can measure operational performance and identify bottlenecks.

## Acceptance Criteria

1. **Volume over time** - API returns signal counts grouped by day and `signalReason` for a configurable date range (7d, 30d, 90d)
2. **Resolution velocity** - API returns median time-to-resolve (hours) per `signalReason`, calculated from `resolvedAt - createdAt` on resolved signals
3. **Resolution rate** - API returns percentage of signals resolved within 24h, 48h, and 1 week per reason
4. **Priority distribution** - API returns count breakdown by priority level (CRITICAL/HIGH/MEDIUM/LOW) per reason
5. **Role engagement** - API returns per-role signal counts and resolution rates, derived from user role join on signal `userId`
6. **Top entities** - API returns entities ranked by unresolved signal count with entity name and type
7. **Filter support** - All endpoints support filters: `range`, `role`, `incidentId`, `entityId`, `signalReason`
8. **Zod validation** - Query parameters validated with Zod schema
9. **Performance** - Analytics queries complete in <2s with 10k+ signals

## Tasks / Subtasks

- [ ] **Task 1: Zod Validation Schema** (AC: 7, 8)
  - [ ] Create `src/lib/validation/signal-analytics.ts` with `SignalAnalyticsQuerySchema`
  - [ ] Fields: `range` (enum: 7d/30d/90d, default 7d), `role` (optional SignalTargetRole), `incidentId` (optional uuid), `entityId` (optional uuid), `signalReason` (optional SignalReason)
  - [ ] Export `SignalAnalyticsQueryInput` type

- [ ] **Task 2: SignalAnalyticsService** (AC: 1-6, 9)
  - [ ] Create `src/lib/services/signal-analytics.service.ts`
  - [ ] `getVolumeOverTime(filters)` — group `ActionSignal` by `DATE(createdAt)` and `signalReason`, return `{ date, reason, count }[]`
  - [ ] `getResolutionVelocity(filters)` — median of `resolvedAt - createdAt` in hours, grouped by reason
  - [ ] `getResolutionRate(filters)` — percentage resolved within 24h/48h/1w, grouped by reason
  - [ ] `getPriorityDistribution(filters)` — count by priority per reason
  - [ ] `getRoleEngagement(filters)` — join `User → UserRole` on `userId`, count and resolve rate per role
  - [ ] `getTopEntities(filters)` — group by `entityId` where `resolvedAt IS NULL`, join `Entity` for name/type, order by count desc, limit 20
  - [ ] `getFullAnalytics(filters)` — aggregates all above in one call with parallel `Promise.all`
  - [ ] All methods accept `SignalAnalyticsQueryInput`, derive date range `WHERE createdAt >= now() - range`

- [ ] **Task 3: API Route** (AC: 1-8)
  - [ ] Create `src/app/api/v1/signals/analytics/route.ts`
  - [ ] `GET` handler: parse query with `SignalAnalyticsQuerySchema`, call `SignalAnalyticsService.getFullAnalytics()`, return `{ success, data }` envelope
  - [ ] Auth guard: require COORDINATOR or ADMIN role
  - [ ] Error handling: 400 for invalid params, 500 for query failures

- [ ] **Task 4: Unit Tests** (AC: 1-6, 9)
  - [ ] `tests/unit/services/signal-analytics.test.ts`
  - [ ] Test each analytics method with seeded data
  - [ ] Verify median calculation correctness with odd/even signal counts
  - [ ] Verify resolution rate bucket boundaries (24h, 48h, 1w)
  - [ ] Verify performance with 10k mock signals (target <2s)

## Dependencies
- Existing `ActionSignal` model with indexes on `[userId, resolvedAt]`, `[userId, entityId]`, `[userId, priority]`

## Technical Notes
- Uses existing `prisma` client from `@/lib/db/client`
- Aggregation uses Prisma `groupBy` + raw SQL for median (Prisma doesn't support MEDIAN natively — use `$queryRaw` with `PERCENTILE_CONT(0.5)` on PostgreSQL)
- Date range filtering: `createdAt >= {now - range}` applied to all queries
