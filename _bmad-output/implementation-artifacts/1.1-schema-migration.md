# Story 1.1: Schema Migration — ActionSignal, Notification, PushSubscription, PlanCommitment + Commitment Fix

Status: ready-for-dev

## Story

As a developer,
I want to create the database schema foundation (4 new Prisma models + migration + commitment model fixes) for the Action-Driven Dashboards feature,
so that all downstream stories (signal engine, dashboards, notifications, offline) have the data layer ready to build on.

## Acceptance Criteria

1. **AC1: Four new Prisma models created** — `ActionSignal`, `Notification`, `PushSubscription`, `PlanCommitment` added to `prisma/schema.prisma` with exact fields, relations, indexes, and table mappings as specified in the architecture document (AD-1 through AD-5)
2. **AC2: PlanCommitment junction table replaces RapidResponse.commitmentId** — `PlanCommitment` model with `planId` (FK to RapidResponse) and `commitmentId` (FK to DonorCommitment) with `@@unique([planId, commitmentId])`, `onDelete: Cascade` on both sides; `commitmentId` and `donorId` fields removed from `RapidResponse`; `"CommitmentResponses"` relation removed from both models
3. **AC3: DonorCommitment.items gains deliveredQuantity** — `CommitmentItem` TypeScript interface extended to `{ name: string; unit: string; quantity: number; deliveredQuantity: number; estimatedValue?: number }`; existing rows with old shape continue to work (deliveredQuantity defaults to 0 in application code, not via migration)
4. **AC4: Migration seeds PlanCommitment from existing FK data** — Migration script creates `PlanCommitment` rows for every `RapidResponse` where `commitmentId` is non-null, then drops the `commitmentId` and `donorId` columns from `rapid_responses` table
5. **AC5: ActionSignal model with unique constraint** — `@@unique([userId, entityId, incidentId, type, signalReason])` enables upsert behavior; `@@index([userId, resolvedAt])`, `@@index([userId, entityId])`, `@@index([userId, priority])` for query performance
6. **AC6: Notification model with expiry** — 24h auto-expiry via `expiresAt DateTime`; `@@index([userId, readAt])`, `@@index([userId, expiresAt])` for unread count queries; FK to `ActionSignal` via `signalId`
7. **AC7: PushSubscription model** — `endpoint` unique constraint; stores `p256dh`, `auth`, `browserInfo` as strings; FK to User
8. **AC8: TypeScript types generated** — `npx prisma generate` succeeds; all new models produce correct TypeScript types
9. **AC9: Existing app compiles** — All existing code that referenced `RapidResponse.commitmentId` / `RapidResponse.donorId` / `RapidResponse.commitment` / `RapidResponse.donor` is updated to use `PlanCommitment` junction table pattern instead; `npm run build` succeeds with zero errors
10. **AC10: web-push npm package installed** — Added to `package.json` dependencies

## Dev Notes

### Architecture Decisions to Follow

- **AD-3: PlanCommitment junction table** — Clean normalized schema. No backward compatibility burden since first deployment hasn't happened. User preference for clean architecture over migration compatibility. [Source: architecture-action-driven-dashboards.md AD-3]
- **AD-1: Signal generation via service hooks** — ActionSignal model supports upsert via unique constraint. `evaluateAndGenerate()` will use this. [Source: architecture-action-driven-dashboards.md AD-1]
- **AD-5: Separate Notification model** — Notification lifecycle (read/dismiss/expiry) is orthogonal to signal lifecycle (active/resolved). [Source: architecture-action-driven-dashboards.md AD-5]

### Exact Model Definitions (from Architecture Document)

```
ActionSignal {
  id             String    @id @default(uuid()) @map("id")
  userId         String    @map("user_id")
  entityId       String    @map("entity_id")
  incidentId     String?   @map("incident_id")
  type           String    // AssessmentType or ResponseType
  signalReason   String    // Enum string
  priority       String    // CRITICAL, HIGH, MEDIUM, LOW
  context        Json      // Reason-specific payload
  createdAt      DateTime  @default(now()) @map("created_at")
  resolvedAt     DateTime? @map("resolved_at")

  user           User      @relation(fields: [userId], references: [id])
  entity         Entity    @relation(fields: [entityId], references: [id])
  incident       Incident? @relation(fields: [incidentId], references: [id])

  @@unique([userId, entityId, incidentId, type, signalReason])
  @@index([userId, resolvedAt])
  @@index([userId, entityId])
  @@index([userId, priority])
  @@map("action_signals")
}

Notification {
  id          String    @id @default(uuid()) @map("id")
  userId      String    @map("user_id")
  signalId    String    @map("signal_id")
  title       String
  body        String
  priority    String
  readAt      DateTime? @map("read_at")
  dismissedAt DateTime? @map("dismissed_at")
  createdAt   DateTime  @default(now()) @map("created_at")
  expiresAt   DateTime  @map("expires_at")

  user        User        @relation(fields: [userId], references: [id])
  signal      ActionSignal @relation(fields: [signalId], references: [id])

  @@index([userId, readAt])
  @@index([userId, expiresAt])
  @@map("notifications")
}

PushSubscription {
  id          String   @id @default(uuid()) @map("id")
  userId      String   @map("user_id")
  endpoint    String   @unique
  p256dh      String
  auth        String
  browserInfo String?  @map("browser_info")
  createdAt   DateTime @default(now()) @map("created_at")

  user        User     @relation(fields: [userId], references: [id])

  @@map("push_subscriptions")
}

PlanCommitment {
  id            String   @id @default(uuid()) @map("id")
  planId        String   @map("plan_id")
  commitmentId  String   @map("commitment_id")
  createdAt     DateTime @default(now()) @map("created_at")

  plan          RapidResponse   @relation(fields: [planId], references: [id], onDelete: Cascade)
  commitment    DonorCommitment @relation(fields: [commitmentId], references: [id], onDelete: Cascade)

  @@unique([planId, commitmentId])
  @@map("plan_commitments")
}
```

### Migration SQL Strategy

The migration must run in this order:
1. Create `plan_commitments` table (with FKs to `rapid_responses` and `donor_commitments`)
2. Seed `plan_commitments` from existing data:
   ```sql
   INSERT INTO plan_commitments (id, plan_id, commitment_id, created_at)
   SELECT gen_random_uuid(), rr.id, rr.commitment_id, NOW()
   FROM rapid_responses rr
   WHERE rr.commitment_id IS NOT NULL;
   ```
3. Drop `commitment_id` column from `rapid_responses` (this also removes the index)
4. Drop `donor_id` column from `rapid_responses`

### Critical Warnings

1. **No data loss** — The migration seeds PlanCommitment BEFORE dropping columns. Test with existing data.
2. **First deployment** — This is a brownfield system but has not been deployed to production yet. Clean break is acceptable per user preference.
3. **DonorResponse relation** — If `Donor` model has a `responses RapidResponse[]` relation via `"DonorResponses"`, that must also be removed and replaced with an indirect relation through PlanCommitment.
4. **Incident.metadata** — The `Incident` model already has a `metadata Json` field. Population cadence (`populationAssessmentCadenceHours`) will be stored there — no schema change needed for FR-4.
5. **Notification.title/body column types** — Use `String` not `@db.Text` — notification templates produce short strings (< 200 chars).
